GrowthBook's **AI-based Visual Editor** is a no-code way to build and launch experiments on your website. Describe the change you want in plain English, review what the editor proposes, and ship a real A/B test without writing code or waiting on a deploy.

We built it so **non-technical teammates** can create variants in minutes: marketers, PMs, and growth teams prompt changes to text, images, buttons, and layout, then preview and launch like any other GrowthBook experiment. Every accepted edit shows up in a **Changes** list so you always know exactly what will reach users.

:::tip Early access on GrowthBook Cloud

The AI Visual Editor is available to try **free during early access** on [GrowthBook Cloud](https://app.growthbook.io). Self-hosted deployments require an Enterprise plan and your own AI provider configuration. See [What you need](#what-you-need) below.

:::

## Why teams use it

- **Empower non-technical users**: Create website variants in minutes without filing an engineering ticket for every copy or layout test.
- **Prompt-driven editing**: Describe changes to text, images, buttons, spacing, and more in [AI mode](/app/visual/ai-mode). Pin an element when you want the AI to focus on a specific spot on the page.
- **Learn from past experiments**: The editor can draw on prior tests in your organization to suggest direction (rolling out). See [Learning from past experiments](/app/visual/ai-mode#learning-from-past-experiments).
- **Run experiments without dedicated eng time**: Draft and QA variations in the browser; your site still needs the GrowthBook SDK for production delivery. See [Running on your site](/app/visual/running-on-your-site).
- **Transparent by design**: Every change is listed with a clear diff. Nothing ships silently. See [Preview and QA](/app/visual/preview-and-qa).

## Benefits

- **No-code experimentation**: Test ideas on your site without a heavy code lift from engineering.
- **AI-assisted drafting**: Describe intent in plain language ("make this CTA feel more urgent") and review proposed edits before you accept them. See [AI mode](/app/visual/ai-mode).
- **Manual precision**: Fine-tune typography, spacing, links, and visibility with structured controls when you know exactly what you want. See [Manual mode](/app/visual/manual-mode).
- **Production delivery**: Variations render through the same GrowthBook SDK you use for feature flags and experiments.
- **Built-in QA**: Preview links, a debug panel, and warnings when you edit a live experiment. See [Preview and QA](/app/visual/preview-and-qa).

## How it works

1. **Install and connect** the [GrowthBook Visual Editor extension](/app/visual/install-and-connect) to your GrowthBook account.
2. **Create a visual experiment** in GrowthBook and open the editor against your target URL.
3. **Design variations** with [AI mode](/app/visual/ai-mode), [Manual mode](/app/visual/manual-mode), or both.
4. **Install an SDK** on your site so variations render for real users. See [Running on your site](/app/visual/running-on-your-site).
5. **Preview, launch, and analyze** the experiment in GrowthBook like any other A/B test.

## When the Visual Editor is not the right tool

The Visual Editor is built for **targeted A/B tests on a specific page**, not full site redesigns.

**Do not use it when:**

- **You want a wholesale redesign.** AI mode is powerful, and it is tempting to ask for "redesign the whole homepage." That scope is better handled in your design system or codebase. Use the editor to test one hypothesis at a time: a headline, a hero image, a CTA style.
- **Your app is heavily client-side rendered** and you cannot use an [Edge SDK](/lib/edge/cloudflare). Framework re-renders can fight visual mutations. For complex React/Vue/Svelte apps, [Feature Flags](/app/features) in code are usually more reliable.
- **You need native mobile, desktop, or email.** The editor only works on front-end web pages in a desktop browser.
- **You need pixel-perfect design handoff from Figma as production code.** Figma import is experimental and rebuilds from exported images, not your site's components. See [Figma import](/app/visual/ai-mode#figma-import).

**Right-sized examples:**

- Test a more urgent hero headline.
- Swap hero photography for a lifestyle shot.
- Make the primary button larger and higher contrast.
- Hide a secondary nav item for a segment.

## Pitfalls and guardrails

Visual experiments can change what real users see on a live site. Treat the editor like production tooling.

- **You can break a page.** A bad CSS change, a hidden checkout button, or an image that does not load can hurt conversion. Always preview each variation on the real URL before launch.
- **Approval flows are coming.** Experiment-level approvals (similar to [flag publishing workflows](/features/publishing-and-approval-flows)) will add a review gate before changes go live. Until then, restrict who can start experiments in your org.
- **Live edits are immediate.** If you edit a **running** experiment, bucketed users can see the update on their next SDK refresh. See the amber warning in [Preview and QA](/app/visual/preview-and-qa#the-live-experiment-editing-warning).
- **We show every change.** The Changes panel and AI diff cards list exactly what will ship. Review them like you would a pull request.

### URL targeting

GrowthBook needs to know which page URLs an experiment should run on. You set a representative URL for editing in the Visual Editor and a targeting pattern for which URLs the SDK should match in production.

The new side-panel editor uses the same URL targeting rules as the GrowthBook experiment form. For wildcards, query strings, and regex mode, see [Experiment configuration](/experimentation-analysis/experiment-configuration) and the [legacy Visual Editor URL targeting section](/app/visual/legacy#url-targeting).

## Stopping an experiment and shipping the winner

When you stop a visual experiment, you can optionally enable a **Temporary Rollout** that sends 100% of eligible traffic to the winning variation through the SDK.

Treat rollouts as temporary. Re-implement the winning change in your site's code when you can:

- **Faster renders**: Code changes paint with the initial HTML instead of waiting on SDK mutations.
- **Better SEO**: Crawlers see the shipped variation in markup, not only after JavaScript runs.
- **Smaller SDK payloads**: Stopped visual experiments stay in the connection payload until you clean them up.
- **Fewer conflicts**: Two live visual experiments targeting the same element can clash. Code ownership avoids that.
