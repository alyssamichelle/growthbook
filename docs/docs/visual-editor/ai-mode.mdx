AI mode is the core of GrowthBook's **AI-based Visual Editor**. Describe what you want in plain English ("make the hero headline more urgent and the primary button green"), and the editor proposes specific changes to text, images, buttons, and styles. You preview each proposal live, then accept, edit, or reject it before anything is saved to the variation.

The goal is **better UX than before**, not a full redesign. Describe the outcome you want ("more urgent," "more premium," "less cluttered") and let the AI propose concrete edits. If you ask for an entire page overhaul, results will be unfocused and hard to ship as a clean experiment.

AI mode is especially good for:

- Changing **text, images, buttons**, and layout from a single prompt
- Multi-property changes ("make this card more premium") without touching each control
- Teammates who do not want to think about CSS selectors or the manual property panel

You can mix AI mode and [Manual mode](/app/visual/manual-mode) freely within the same variation. Accept the AI's draft, then jump into Manual mode to fine-tune.

## Prerequisites

Before AI mode is usable on your account:

1. **An org admin needs to configure an AI provider.** Go to **Settings → General → AI Settings** in GrowthBook and add an OpenAI, Google, or xAI API key. See [AI Integrations](/integrations/ai) for the full setup.
2. **Your plan must include AI features.** AI mode is part of the `ai-suggestions` commercial feature. Pro and Enterprise plans include it; Free does not.
3. **You need to be connected** to your GrowthBook account in the [Visual Editor side panel](/app/visual/install-and-connect).

If AI mode is greyed out in the side panel, the most common cause is that no AI provider key is configured yet for the organization.

## Opening AI mode

After you open the side panel and target a URL, you'll see two top-level tabs: **AI** and **Manual**. AI is selected by default.

The AI panel has three parts:

- A **prompt box** at the top of the panel where you describe what you want.
- A **chat log** that fills in as you make requests — each turn shows what you asked, followed by an assistant card with the proposed changes.
- The **Changes panel** at the bottom of the side panel, which lists every change accepted so far for the current variation.

When the chat log is empty, the prompt area also surfaces a few **suggested prompts** and **quick actions** to help you get started.

## Writing good prompts

The AI does its best work when you describe **intent and location**, not implementation details.

**Good:**

- `Change the hero headline to something more urgent and benefit-led`
- `Make the primary CTA button bright green and a little larger`
- `Hide the secondary nav links on the right`
- `Make this card feel more premium without changing the layout`

**Less good:**

- `Make the page better` — too vague; the AI will guess and the result will be unfocused.
- `Redesign the entire homepage` — out of scope for a single visual experiment. Break the idea into smaller tests.

### Nebulous prompts

You do not have to spell out every CSS property. Prompts like "make this feel more playful" or "this section looks dated" are valid starting points. The AI interprets intent and proposes specific edits you can accept, reject, or refine in a follow-up turn.

We are still learning which prompt styles work best across teams. Expect the experience to keep improving as we collect feedback and tune models.

**Tips that consistently improve results:**

- **Name the element by what it is, not how it's coded.** "The hero headline" works; ".hero h1" rarely needs to be in the prompt.
- **Describe intent.** "More urgent," "more premium," "more playful" gives the AI a direction.
- **Ask for variants.** "Give me three options" or "draft a few alternatives" produces multiple suggestions in one turn.
- **Chain prompts.** A second prompt can refine the first ("the green is too neon — make it more muted").

:::tip "Set the title" targets the H1

If you say something like "set the title to X," the AI targets the visible `<h1>` (or the most prominent heading) — not `document.title`. To change the browser tab title, say so explicitly: "change the page's browser tab title to X."

:::

## Suggested prompts and quick actions

When the chat log is empty, the panel shows two helpers:

- **Suggested prompts** — short example prompts you can click to send as-is. These are tuned to common A/B test ideas.
- **Quick actions** — one-click shortcuts for the most common patterns (e.g., "Generate a new image," "Suggest three headlines").

Both are designed to help less technical users get past the blank prompt box.

## Adding element context to a prompt

Below the prompt box is a **Select element** button (with an `@` icon). Click it and then click any element on the page — that element gets pinned to your prompt as **context**. A small chip appears above the prompt box showing what you picked. You can pin multiple elements, and remove individual chips with the **×** on each chip.

When you send a prompt with elements pinned, the AI treats those elements as the **authoritative target** for the change. Your prompt describes _what to do_; the chips tell the AI _where to do it_.

Pinning elements scopes the AI's attention. It does **not** restrict the AI to only those elements for the rest of the session. You can still ask for page-wide changes in a later turn without re-pinning.

This is one of the most powerful features of AI mode, and it's worth using whenever:

- **The page has ambiguous elements.** Multiple headlines, multiple "Submit" buttons, repeated card components. Saying "change the headline" is ambiguous; picking the specific headline first removes the guesswork.
- **You want to isolate a change.** Without context, the AI looks across the whole page and may propose changes to elements you didn't intend to touch. Pinning the element you care about scopes the change to just that element.
- **The AI keeps targeting the wrong element.** If a previous turn picked the wrong target, pin the right one and re-prompt — the chip overrides whatever the AI inferred from the prompt text alone.
- **You're working on a specific component.** Pin the card, ask for "three alternative layouts for this card," and every proposal will be scoped to the card you picked.

### Example: ambiguous headlines

A pricing page has two headlines — a hero headline at the top and a feature-section headline lower down. A prompt like _"make the headline more urgent"_ is ambiguous; the AI will pick one based on heuristics and may pick the wrong one.

Instead:

1. Click **Select element**, then click the hero headline. A chip appears.
2. Type the prompt: _"Make it more urgent and benefit-led."_
3. Send.

The AI now operates only on the element you pinned. No guessing.

### Example: scope a change to a single card

A product grid has nine identical cards. You want to test a "featured" treatment on just one of them:

1. Click **Select element**, then click the card you want to feature. A chip appears.
2. Type the prompt: _"Make this card stand out — bold border, slightly larger, a 'Featured' badge in the top-right corner."_
3. Send.

Without context, the AI might apply the change to all nine cards (or worse, propose CSS that targets the parent grid). With the card pinned, the change is surgical.

### Picking multiple elements

You can pin more than one element. Useful when:

- You want the same change applied to several specific elements ("make these three buttons match the primary style").
- You're describing a relationship ("move this image so it sits next to this paragraph").

Each picked element gets its own chip. Remove any chip with the **×** to drop it from the prompt's context without re-picking from scratch.

### Combining with the chat history

Element context is sticky within a turn but not across turns — once you send a prompt, the chips clear and the AI's understanding of "this element" carries forward through the chat history. So a typical flow is:

1. Pin the hero headline → prompt: "make it more urgent." Send.
2. (No need to re-pin.) Prompt: "now also make it slightly larger." Send. The AI still knows you mean the hero headline.
3. To switch targets, click **Select element** again and pick a different one.

## Reviewing proposed changes

When the AI returns, it adds an assistant card to the chat log. The card contains:

- A short summary of what was changed and why.
- One or more **diff cards** — each represents a single DOM change (a text edit, a style change, an attribute change, etc.). The diff card shows the element it targets and what's being set.

Each proposed change is **previewed live on the page** as soon as it lands. You do not have to accept first to see the result.

For each change you can:

- **Accept** — the change moves into the Changes panel as part of the current variation.
- **Reject** — the preview is reverted and the change is dropped.
- **Edit** — open the change in Manual mode to tweak values before accepting.

Reject doesn't end the conversation. You can ask for a different version ("more subtle — keep the original color, just bump the size") and the AI will produce a new proposal.

## Selector grounding and SPAs

When the AI proposes a change, it picks a CSS selector and validates it against the actual page DOM. If the selector does not match a real element, the change is rejected before it reaches you.

We prefer **stable selectors** (semantic tags, durable classes, `data-*` attributes) over brittle ones (deep `nth-child` chains, framework hash classes). That matters on **single-page apps**: when React, Vue, or similar frameworks re-render the DOM, the GrowthBook SDK watches for those mutations and **re-applies** your variation to matching elements. See [How variations stick on dynamic pages](/app/visual/running-on-your-site#how-variations-stick-on-dynamic-pages).

If a proposal looks wrong, you can usually fix it by either (a) saying so in the next prompt ("you targeted the footer headline — I meant the hero"), or (b) picking the right element manually first and re-asking.

## Figma import

:::warning Not production-ready

Figma import is experimental and not recommended for production experiments yet.

:::

Figma import lets you bring a design into the editor as a starting point. Today it works by pulling **exported images** from Figma and rebuilding layout in the page. It does **not** import your production React/Vue components or design-system code.

That tradeoff means:

- **Faster mockups** for "what if we tried this layout?" exploration.
- **More cleanup** before launch compared to editing the live page directly.

Generic HTML insertion into `document.body` can fight the SDK's mutation observer (insert → observer fires → re-insert → loop). The Figma flow uses **custom JavaScript** for imports to avoid that loop. [alyssa fill out more here: document the Figma import UI once it is customer-ready.]

## Multi-turn conversations

The chat log keeps the full thread for the current variation. You can layer changes:

```
You: change the hero headline to something more urgent
AI:  [proposes new headline]
You: also make the headline larger
AI:  [proposes a font-size change on the same element]
You: actually undo the size change and just bold it instead
AI:  [reverts size, proposes font-weight]
```

Each new turn sees the prior turns, so refinements work. If you want a clean slate, start a new variation.

## Image generation

If you ask the AI to swap a hero image, generate product imagery, or anything else that requires a new image, AI mode hands off to the image-generation flow. You'll pick from one or more configured image models, optionally use the existing image as a visual reference, and accept the result into the changeset the same way as any other change.

### Brand guidelines / additional context

Free-text context prepended to **every** Visual Editor AI call: text edits in the extension and image generation. Use it to steer tone, palette, and CTA rules without repeating them in each prompt.

Example:

```
We're a B2B SaaS company. Brand colors: #6E56CF and #1F2D5C.
Sentence-case CTAs. Friendly but professional tone.
```

Available on **GrowthBook Cloud and self-hosted**.

### Visual editor text model

Controls which model powers AI chat edits and suggestions in the extension. Leave **Use default AI model** to inherit the org-wide default from the same settings page.

| Deployment | Can override text model? |
| ---------- | ---------------------- |
| **Self-hosted** | Yes. Pick any model your org has API keys for. Useful when the default feels too literal on vague prompts; a more capable model often interprets intent better at higher cost. |
| **GrowthBook Cloud** | No. Cloud uses GrowthBook-managed models. This dropdown is not shown. |

### Visual editor image model

Controls which model generates images in the extension. Models that support **reference images** can use the current on-page image as visual context (the "use current image" flow). Text-only models generate from the prompt alone.

| Deployment | Can override image model? |
| ---------- | ----------------------- |
| **Self-hosted** | Yes. Choose from supported image models (e.g. Gemini, Imagen, DALL·E, GPT Image). |
| **GrowthBook Cloud** | No. Cloud uses GrowthBook-managed defaults. |

See [Images → Available image models](/app/visual/images#available-image-models) for the full list and reference-image support.

Click **Save All** at the bottom of the settings page after changing any of these fields.

## What gets sent to the AI

For each prompt, the back-end sends to the configured AI provider:

- Your prompt text
- A simplified snapshot of the relevant DOM (typically the elements visible in the viewport, plus any selected element)
- The URL of the page being edited
- Optionally, a small system prompt that biases the model toward stable, accessible changes

Your GrowthBook experiment metadata, metric values, user data, and SDK payloads are **not** sent. The connection uses your org's configured AI provider key — see [AI Integrations](/integrations/ai) for the full data-sent inventory.

## Limits and caveats

- **Single-page scope.** AI mode reasons about the page currently loaded in the Visual Editor's target URL. It cannot propose changes against pages it has not seen.
- **Not a redesign tool.** Keep experiments focused. One headline, one hero, one CTA at a time ships cleaner than "redo everything."
- **Selectors can still drift.** Large site rewrites or design-system changes can break previously stable selectors. Re-check long-running experiments after major releases.
- **Custom JS does not "un-run."** JavaScript injected for a variation stays active until you refresh the page or navigate away. You may see JS-driven effects persist between elements until reload. Prefer DOM mutations for declarative changes when possible.
- **DOM mutations vs. JS on the same element.** If both target the same selector and attribute, the mutation observer wins and can overwrite one-shot JS. The AI avoids emitting both; if you add JS manually, do not also mutate the same property.
- **Image models cannot take exact pixel dimensions.** Models pick aspect ratio and size heuristically from the original image. Override dimensions afterward in Manual mode if needed.
- **Quality varies by model.** Bigger models handle vague prompts better but cost more. Self-hosted admins can change models; Cloud uses managed defaults.
- **AI mode is not a substitute for review.** Always preview on a real page (and a preview link) before publishing.
